# 值日代做：雙方確認的當週交接

2026-09-14 更新：恢復自動輪值、移除每週管理員核准；詳細管理紀錄限 Admin 讀取並預設收合。依使用者要求，代做不交換輪值、不抵扣未來週次；原值日生邀請一人，對方本人接受後才變更該週執行者。

## 核心規則

1. 原排定者 `scheduled_to` 保留，實際執行者 `assigned_to` 在接受成功時切換。正常輪值與已排定未來週次皆不受代做影響。
2. 限本週、已建立的排班、未提交且未順延的清單，不需每週人工核准。週界採 Asia/Taipei，週一 00:00 至下週一 00:00。
3. 只有當下實際執行者可以提出邀請；一次只能有一個有效待回覆邀請。不能邀請自己。
4. 對象為已核准且 Active 的實驗室成員，可包含 Admin／博士生；代做名單不直接套用只包含非 Admin 碩士生的正常輪值名單。未綁定、未核准、停用與離校帳號不列入。
5. 邀請不代表交接。等待回覆時，原執行者仍負責並可編輯／完成。受邀者可以查看當週清單，但不能先編輯。
6. 只有指定的本人可接受／婉拒。接受成功後，原執行者改為唯讀，受邀者取得當週工作編輯與提交權限。Admin 的管理能力保持獨立。
7. 已勾選項目、補給狀態與公共留言原樣保留，交接不清空清單、不把整週工作都歸為代做者已完成。
8. 已接受不能由原發起者單方面撤回。現任執行者若需再找人協助，重新走一輪邀請及接受；保留完整 A → B → C 的交接紀錄，原排定仍為 A。
9. 不產生「欠班」或交換承諾。B 協助 A 後，B 原本的輪值照常；若 B 之後想請 A 協助，屆時另行邀請 A。

## 畫面互動

### 值日生本人

本週清單上方、姓名附近提供「請人代做」。視窗顯示當週日期、現在由誰負責，以及可搜尋的人選。交接事項選填並註明僅邀請雙方及管理員可見，不把私人理由混入所有成員可讀的公共留言。

送出前顯示：「對方接受前，本週仍由你負責；接受後會保留目前進度，只交接這一週，不影響輪值順序。」按鈕為「送出邀請」。儲存尚未送出的清單／公共留言後才能送出邀請，儲存失败時保留草稿並停止。

待回覆卡片顯示「已邀請 B，等待回覆」及「取消邀請」。想改邀另一人時明確取消舊邀請，再選人送出；不提供可以悄悄更換受邀者的編輯功能。

### 受邀者

登入總覽上方出現「A 邀請你協助本週值日」，值日入口帶待回覆數字；值日頁也有同一張卡片。顯示週期、發起者、最新完成數與剩餘項目摘要、交接事項，提供「查看本週清單」、「婉拒」、「接受代做」。

按接受後，再用頁內確認視窗顯示交接後責任與既有進度。按「確認接受」才提交；收到伺服器成功結果後，卡片變為「本週由你代做」，可直接繼續清單。

婉拒不要求填理由；發起者看到「B 已婉拒，你可以另邀其他人」。取消／婉拒後不再顯示操作按钮，但保留雙方可看的結果，避免舊分頁讓人誤以為還在等待。

### 其他成員與歷史紀錄

已接受後，核准成員可查看本週實際執行 B 與原排定 A。完成紀錄另外顯示最後提交者與提交時間，避免把原本 A 已做的部分誤算為 B 全做。

逐筆交接與管理員改派事件僅 Admin 可讀，畫面使用收合的「管理紀錄」，不用外凸列表圓點。取消、婉拒與私人交接事項只對當事人與 Admin 開放；主畫面顯示目前待處理邀請或最後一筆婉拒／取消結果。完整事件仍保留姓名及學號快照供管理追蹤。

第一版採站內通知與即時更新，不宣稱已寄信或傳送外部通知；日後若加郵件，再實作後端可靠投遞與防重寄。

## 狀態與衝突處理

| 情況 | 結果 |
|---|---|
| 邀請送出 | 等待本人回覆；原執行者不變 |
| 受邀者接受 | 一次完成交接，鎖定此邀請的接受結果 |
| 受邀者婉拒 | 原執行者不變，可重新邀請 |
| 發起者取消 | 原執行者不變；舊接受按鈕不可使用 |
| 原執行者先提交完成 | 待回覆邀請失效，不再允許接受 |
| 管理員改派或紀錄順延 | 待回覆邀請失效，不套用到新指派／下一週 |
| 跨至下週 | 未接受邀請到期；伺服器依時間拒絕，不能只靠畫面計時器 |
| 任一方失去核准或 Active 身分 | 邀請失效，不自動指派給其他人 |
| 帳號解除／重新綁定或學號移轉 | 舊邀請失效，重新核對新身分後才能邀請 |
| 同時按取消與接受 | 以第一個成功的交易為準；另一方讀回實際結果 |
| 同時按提交與接受 | 只允許其中一個成功；禁止已提交後改執行者 |
| 舊邀請取消後再邀同一個人 | 使用全新的邀請識別碼；舊頁面不能接受新邀請 |
| 重複點擊、重新整理或回應遺失 | 同一操作只生效一次；讀回已接受結果，不產生重複歷史 |
| 交接時原執行者還在編輯 | 成功交接後停用其編輯；尚未送出的草稿保留讓本人複製，不覆蓋 B 的資料 |

接受時以最新清單為準，交易只改交接必要欄位，不把受邀者先前看過的舊清單整份寫回。進度一般更新不讓邀請失效；實際執行者改變或排班重建才使指派版本變動。

到期／撤權造成的失效必須即使沒有背景排程也成立；可以依目前週期、授權及指派版本判定有效狀態，不能因沒有背景程序把狀態字串改為 expired 就繼續允許接受。

## 代做與順延

代做同意僅涵蓋邀請上寫明的那一週。跨週不自動要求 B 繼續協助，也不自動替 B 接受新邀請。

未完成時自動由原排定者 A 順延；要繼續請 B 協助，於新週再邀請並由 B 接受。保留上週進度並鎖定舊週，新週建立空白清單。介面區分本週實際執行者與原輪值者，不能只讀 assigned_to 就把 B 帶到下一週。

正常輪值的下一位仍按 scheduled_to 決定；代做本身不移動名單、不消耗 B 的正常輪值。

`duty_rotation/current` 保存管理員維護的循環名單（first／successors）及已建立週次。核准成員首次開啟新週時，以交易建立指派與清單、更新週次，必要時鎖定上週；規則驗證台北當週及確切人選。既有本週紀錄、Admin 預排优先，不覆蓋進度。無人開啟的空週不消耗輪值。這是開啟系統時自動接續，不是背景排程；成員名單更動後由 Admin 畫面自動同步循環順序。

發布時先備份規則、成員名錄與值日資料，切換新版規則，再以目前已建立的最新週次初始化唯一指標；不得重排或刪除既有值日紀錄。最後部署 approved 網站並核對線上建置。僅部署網站不會發布 Firestore Rules。若回復，應成套還原相容的網站與規則，保留值日資料及指標備份供核對。

## 管理員操作

管理員可以取消問題邀請或用獨立的「管理員改派」處理例外，但不能替受邀者按接受，也不能把管理員改派記成雙方已同意的代做。改派要顯示原人選、新人選、影響週次、保留進度及使待回覆邀請失效，並留下操作者與原因。

saveCurrentDutyAlignment／saveApprovedDutyAssignment 的一般改派已改為保留進度與留言，遞增指派版本並新增獨立管理員事件。完成紀錄維持鎖定。

## 資料與權限實作要求

- 保留 duty_records／duty_assignments 的原排定及實際執行者，同步更新必要欄位，避免一份仍是 A、另一份已是 B。
- 每筆邀請有獨立 ID、所屬週次、發起者與受邀者的確切核准身分、指派版本、伺服器時間、結果。本人身分不可只比對姓名或前端選單。
- 清單僅持有目前邀請 ID 與指派版本；舊邀請不能藉重複接受、重建指派或改狀態重新生效。
- 接受邀請、雙向指派更新、清單交接、歷史事件，必須於同一原子交易成立。其他動作如取消／提交／管理員改派也須符合完整狀態轉移。
- Firestore Rules 限制欄位及狀態轉移，檢查 request.auth、已核准且 Active、指定本人、週次有效期限及交易前後一致性。不能只新增「成員可改 assigned_to」的廣泛更新許可。
- 開放選人所需的最小資格資訊，不讓一般成員讀取完整 member_access 或私有成員資料。資格投影須隨核准／撤權／離校同步，接受時仍再驗證真實授權，不能單憑投影授權。
- 已接受事件不可回頭改寫，`duty_events` 只有 Admin 可讀；`duty_requests` 仍限制確切當事人及 Admin。一般成員不訂閱管理事件，以值日紀錄呈現原輪值與實際代做者。
- 舊 substitute_pending 不視為新版有效邀請，避免沒有邀請 ID、接受身分或期限的歷史欄位意外取得權限。既有值日歷史保留，缺欄位時顯示合理的舊資料狀態。

## 上線前驗收

先用模擬器驗證 A 邀 B → B 接受 → A 唯讀、B 可編輯提交 → 原輪值及下週安排不變，並驗證全量既有功能回歸。

另外涵蓋自己邀自己、冒名邀請／接受、Guest／未核准／離校對象、邀請狀態競爭、雙重點擊、旧邀請重播、邀請後撤權或換 UID、週一邊界、已完成／已順延、多人連續交接、既有進度／未存草稿、管理員保留進度改派、學號移轉與歷史顯示。

本機 Browser 用不同假資料工作階段驗證通知、按鈕狀態、即時交接及管理紀錄收合；Firestore 模擬器驗證真實 helper 的邀請、接受、提交與自動輪值權限。正式發布核對規則及網站建置；不得為驗收擅自更改真實排班或替真實成員接受邀請。沒有操作正式雙帳號時，應明確區分本機測試與正式驗收。
